## Frontend toolchain normalization

The initial manifest combined release lines whose peer ranges did not agree
during a clean install. Phase 0 keeps the same React application and normalizes
only the build/lint toolchain to versions supported by the repository's Node
22 runtime and plugin set. The lockfile was regenerated by npm, not edited by
hand.

| Tool | Initial manifest | Phase 0 manifest | Reason / compatibility |
|---|---:|---:|---|
| `@babel/core` | `^8.0.1` | `^7.29.7` | Stable line compatible with the existing React/Vite plugin chain |
| `eslint` | `^10.7.0` | `^9.39.5` | Supported by the installed React and React Hooks ESLint plugins |
| `@eslint/js` | `^10.0.1` | `^9.39.5` | Kept on the same major line as ESLint |
| `vite` | `^8.1.4` | `^7.3.6` | Supported by `@vitejs/plugin-react` 5 and Node `>=20.19` |
| `globals` | absent | `^17.7.0` | Explicit browser, Node, and test globals for flat ESLint config |

Risk is limited to build-tool behavior rather than application runtime APIs.
The clean install, frontend tests, production build, PWA generation, and npm
audit are required evidence for accepting this normalization.

## Phase ordering risks

1. The worktree already contained uncommitted Phase 3 changes before this audit;
   those changes are not part of the Phase 0 cleanup commit.
2. Assignment flags use truthiness in several components, so the string `false`
   can behave as enabled. Correct boolean parsing is required during Phase 3.
3. API V2 feature flags are referenced in source but are absent from the checked
   production environment example.
4. `/api/db` is still an active compatibility layer and must not be removed.
5. The 42-route V2 baseline includes provisional uncommitted routes and therefore
   must be regenerated after the Phase 3 work is committed or reverted.
